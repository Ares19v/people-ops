# Google ADK Web and Langfuse: two ways to evaluate the same agent

The HR agent fleet (`hr_root_orchestrator` → leave / timesheet / health / policy / zoho sub-agents) can be
evaluated two ways. They answer different questions, so both are wired up and can be compared per case.

| | **ADK Web / ADK evaluators** | **Langfuse experiments** |
|---|---|---|
| What runs | The agent fleet alone | The full pipeline: guardrails, PII redaction, memory, fleet, output clean-up |
| Question answered | *How* did it get there? Which tools, which arguments, how close is the text to a reference? | *Is the answer right, safe and compliant?* |
| Metrics | ADK's built-in evaluators: tool trajectory, response match (ROUGE-1), `final_response_match_v2`, rubric-based response and tool-use quality, hallucinations (LLM-judged ones use `openai/gpt-4o-mini`) | Judge scores: groundedness, helpfulness, statutory compliance, safety, latency |
| Strength | Deterministic, free of judge noise; catches wrong routing, missing/duplicate tool calls, bad arguments | Judges meaning; catches wrong facts, unsafe or non-compliant answers |
| Weakness | Exact match punishes harmless rewording; ROUGE rewards word overlap, not correctness; judge criteria add LLM cost and noise | Cannot see *how* the answer was produced; a wrong tool call can still read fine |
| Where you see it | ADK Web → Eval tab | Langfuse → Datasets → Runs |

> Prompt versions x models on ADK, and GEPA prompt optimisation (DSPy mocked, ADK real): see [prompt_optimization.md](prompt_optimization.md).

## 1. Run ADK Web

```powershell
npm run adk:web                       # or: python scripts/run_adk_web.py --model openai/gpt-4o-mini
```

Open **http://localhost:8010/dev-ui**, choose the **`peopleops`** app. Chat on the left; the event trace shows every
agent hand-off and tool call. Needs the evaluation extras: `pip install -r backend/requirements.txt` (`google-adk[eval]`; on Windows add
`-c .extras/backend/constraints-windows.txt` if Application Control blocks a freshly released binary wheel).

What "the same agent" means here:

* `backend/adk_web/peopleops/agent.py` re-exports the **same `hr_root_orchestrator` object** the backend uses (same
  tools, same Langfuse-managed prompts, hot-reloaded on each turn).
* The production pipeline puts an `[Active Employee … ID: EMP-004]` header and the current time on every message so
  tools receive a real `user_id`. ADK Web sends bare questions, so the identical text is added to the model's system
  instructions (`identity_shim`). Without it the model invents ids and dates.
* **Not included:** the guardrail layer (NeMo), PII redaction and conversation memory. That is a real difference
  between the two legs, and it is why jailbreak/PII cases behave differently.
* **Safety:** ADK Web lets anyone trigger tools that write (apply leave, log hours). The agent module forces an isolated
  SQLite file (`backend/data/adk_web.db`) and refuses to start against anything else. `.env` is loaded by ADK
  with `override=True` before the module is imported, so the override lives in the module itself.

## 2. The Eval tab

Eval sets are generated from the 25 golden cases (`python scripts/build_adk_evalset.py`):

* `peopleops_deterministic` (10 cases): every tool argument is fixed by the question, so ADK's exact-match trajectory
  metric is meaningful. **Start here.**
* `peopleops_golden` (all 25): includes cases where the agent must write free text into a tool argument (a policy search
  phrase, a leave reason, "today's" date). Rewording fails exact match even when behaviour is right.

In the tab: pick an eval set, tick cases, choose the metrics and thresholds, **Run Evaluation**. ADK 2.x shows every
metric's score per case and, for the rubric-based metrics, each rubric's verdict. Clicking a case loads its recorded
session (events/trace), which is where to see what the agent did.

The ADK evaluators in use (`backend/adk_web/peopleops/eval_config.json`, generated by `scripts/build_adk_evalset.py`):

| Criterion | What it checks | Needs an LLM judge |
|---|---|---|
| `tool_trajectory_avg_score` (EXACT) | Ordered tool calls (names and arguments) equal the expectation | no |
| `response_match_score` (0.3) | ROUGE-1 word overlap with the reference answer | no |
| `final_response_match_v2` (0.5) | Is the answer semantically equivalent to the reference? | yes |
| `rubric_based_final_response_quality_v1` (0.7) | Yes/no rubrics: answers the question, no invented facts, first name only, forbidden content, statute, polite refusal | yes |
| `rubric_based_tool_use_quality_v1` (0.7) | Yes/no rubrics: right specialist, employee id not name, no duplicate calls, each tool called once | yes |
| `hallucinations_v1` (0.8) | Share of claims supported by tool results and instructions | yes |

Also reported automatically: `token_usage_v1`, `tool_call_count_v1`, `inference_call_count_v1`,
`invocation_duration_v1`. Not configured: `safety_v1` and `response_evaluation_score` (Google Vertex AI; opt in with
`build_eval_config(include_vertex_metrics=True)` and a GCP project), and the multi-turn criteria
(`multi_turn_*`, `per_turn_user_simulator_quality_v1`, `rubric_based_multi_turn_trajectory_quality_v1`), which need
multi-turn cases or a user simulator; the golden benchmark is single-turn.

Each case carries its own rubrics (from the golden case's forbidden terms, statutory clause, expected tools); the
rules that apply to every case sit in the criteria config. The judge model is whatever LiteLLM name you give
(`--judge openai/gpt-4o-mini`, `groq/openai/gpt-oss-120b`); provider keys from `.env` are exported to the process
environment for ADK (`export_provider_keys_to_env`).

CLI equivalent of the Eval tab (3 representative cases by default; `--all` for the whole set):

```powershell
python scripts/run_adk_eval.py --evalset deterministic --model openai/gpt-4o-mini --judge openai/gpt-4o-mini
```

Expectations (`backend/app/evaluations/adk_expectations.py`) describe what a correct fleet should do (route to the right
sub-agent, call each needed tool once). They are not recordings of today's behaviour. Each case is tagged
`deterministic` and `mutating`.

### Stack notes (ADK 2.x)

* Pinned `google-adk==2.13.0`, `mcp>=2.2`, `langfuse>=4,<5` (ADK 2.x's OpenTelemetry pin conflicts with Langfuse 5).
* ADK 2.x replays the model's earlier "thinking" as `reasoning_content`, which Groq rejects (HTTP 400) on the turn after
  a tool call. `get_llm_model` therefore returns a `LiteLlm` subclass that drops thought parts for Groq.
* ADK 2.x session-service methods are async; `adk_fleet._maybe_await` handles both flavours.
* `ADK_SESSION_DB_URL` (optional persistent sessions): ADK 2.x needs an async driver; plain `postgresql://` / `sqlite:///` URLs are converted automatically (`_async_session_url`).
* `adk eval a/b.evalset.json:id` splits on the first `:`, so use relative paths on Windows.
* The agent's final text sometimes contains the model's reasoning ("The user wants a summary of…") when ADK drives it
  directly; the production pipeline cleans output, ADK Web does not. This lowers ROUGE and some rubric scores.

## 3. Compare ADK and Langfuse

```powershell
python scripts/run_adk_comparison.py --cases BENCH-01-LEAVE-BALANCES,BENCH-09-TIMESHEET-LOG-HOURS --model openai/gpt-4o-mini --judge openai/gpt-4o-mini
```

or `POST /api/v1/agents/experiments/adk-compare` (HR manager/admin; `?wait=true` to block, otherwise poll
`GET …/adk-compare/latest`). Body: `{"items": [...], "model": "...", "judge": "...", "limit": 6}`.

It runs each case through both legs, then reports per case and in aggregate:

* ADK: every criterion above (scores, pass/fail, failed rubrics), tokens and latency. The judge for ADK's LLM
  criteria is the same `--judge` as the Langfuse leg, so the two judges are comparable.
* Langfuse: judge overall score, pass/fail, routed agent, metrics.
* **Agreement**: `both_pass`, `both_fail`, `langfuse_only` (judge accepts, ADK rejects), `adk_only`; plus a correlation
  (needs 3+ cases) between the Langfuse judge score and ROUGE / ADK's rubric quality score.
* The ADK aggregates are written to the Langfuse experiment run as run-level scores (`adk_<criterion>` for every
  criterion, plus `adk_pass_rate`), so **both evaluators appear on the same run in the
  Langfuse UI** (Datasets → peopleops-golden-benchmark-25 → the `adk-compare-…` run).

Cases that write data (apply leave, log hours, Zoho sync) are skipped through the API unless the backend runs on SQLite;
the CLI always uses an isolated SQLite file, so it can include them.

### How to read the disagreements

* `langfuse_only`: the answer reads well, but ADK flags the path (a duplicated call, a wrong tool, or low word overlap
  with the reference). Look at `adk.actual_tools` first: duplicated or missing calls are real defects; low ROUGE alone is not.
* `adk_only`: the path matches but the judge distrusts the answer (e.g. numbers differ from the reference).
* `both_fail`: the strongest signal.
* ROUGE-1 against long reference answers is a weak proxy (it scored correct answers 0.1-0.4). Do not treat a low
  `response_match_score` as wrong; prefer `tool_trajectory` on deterministic cases, `final_response_match_v2` and the rubric
  scores (whose failed rubric ids name the problem).

## 4. First real comparison (gpt-4o-mini, judge gpt-4o-mini, 8 cases; ADK 0.5, trajectory + ROUGE only)

| | Result |
|---|---|
| ADK tool trajectory | 0.75 (0.80 on deterministic cases) |
| ADK response match (ROUGE-1) | 0.18; pass rate 12% at threshold 0.3 |
| Langfuse overall | 0.77; pass rate 62% |
| Agreement | 5 `langfuse_only`, 2 `both_fail`, 1 `adk_only`; correlation judge vs ROUGE = -0.53 (n = 8, indicative only) |

What each evaluator caught that the other did not:

* **Only ADK's trajectory** exposed: `sync_zoho_leave_records` called twice with identical arguments; `apply_leave`
  called with the employee's first name (`'Aarav'`) and `sync_zoho_leave_records` with the full name as `user_id`; the model skipping the balance check
  before applying for leave.
* **Only the judge** can say whether a refusal or a policy answer is actually right and safe. ROUGE scored good answers low.
* Running ADK on the fleet alone also showed what the guardrail layer contributes: ADK Web has none.

## 5. Bugs this work found and fixed

* **Duplicate primary keys after every restart.** Generated ids (`leave_aarav.sharma_1`, `ts_…`, `sess_…`, `aud_…`) came from
  in-memory counters that restarted at 1, colliding with existing rows (the demo data already holds `…_1` and `…_2`), so
  the first new leave application or timesheet entry for an existing employee failed. Counters are now seeded from the
  highest stored index on first use (`app/core/id_generator.py`). If two processes write at the same time they can still
  race.
* **`apply_leave` told users it failed after saving.** It committed the row, then raised building its reply
  (`application.days`; the column is `total_days`), and the error was returned as "Failed to submit". The agent then
  reported failure and retried, which produced duplicate attempts.

## 6. Known gaps

* The model still sometimes passes a name (first or full) as `user_id`, and may repeat a sync call. These are agent-behaviour issues
  surfaced by ADK's trajectory view; they are not fixed.
* ADK Web's own results live in ADK's Eval tab/session store, not in Langfuse. The comparison script is what puts the ADK
  metrics into Langfuse.
* The ADK path does not trace to Langfuse by itself: the comparison's Langfuse leg runs the full pipeline, which does.
